# Plan

## Planned

- Further context-saving ideas for remote MCP (more important there than stdio, since the payload crosses a network to potentially less context-rich clients). Items 1 and 2 are **Done** (see Completed section); 3-5 remain:
  3. Resource links (`type: "resource_link"`) instead of inline data for the biggest payloads — return a URI + short summary, materialize full content only if the agent explicitly reads it. Real payoff for remote MCP (a skippable round trip), but a bigger architectural change (needs a real resource store) and not all clients handle `resource_link` equally well.
  4. Smaller defaults by default, richer fields opt-in — e.g. `get_events` defaulting to `{id, heading, startTime}` and requiring `query`/a `verbose` flag for the rest, flipping today's "everything unless filtered" default. More aggressive savings, but a real behavior/breaking change worth its own discussion, not a drive-by.
  5. Gzip/compression on the HTTP transport — explicitly NOT a context-token fix (the client decompresses to full JSON before it reaches the model), just bandwidth/latency. Noted so it isn't confused with the above.
- CLI status command: Check external dependencies (pdftotext, docx2txt) and that the token works. Do not fail on missing items, just show what is working and what is not.
- Review code for clean separation between input/parsing, logic, integration. Hexagonal style.
- Support for PPT/PPTX files: content conversion (and content search) for PowerPoint files, alongside the PDF/DOCX/XLSX support. Needs a converter tool decision (likely LibreOffice headless — `soffice --headless --convert-to txt`, or `catppt`/similar) since none of the existing pdftotext/docx2txt/ssconvert tools handle presentations.
- `search-files` should also search post attachments, not just the group Files tab. Currently it only calls `getGroupFiles(groupId)` (the shared group file repository) — it misses files attached to individual posts (`post.attachments[]`), which today are only reachable via `get_file` if you already know which post they're on. Needs fetching posts (all types, across groups) alongside group files and feeding their attachments through the same filename/content matching pipeline.
- Token refresh: `spond-mcli login`'s token expires in ~24h and currently requires a full manual re-login — investigated adding real refresh support (see Completed entry below) but the `POST /auth2/login/refresh` endpoint consistently returns a generic `500` regardless of request-body shape, even with a freshly-issued, unconsumed `refreshToken` obtained straight from a real login. Suspected but unconfirmed: a bot-protection/challenge requirement on that endpoint (the web client loads Cloudflare Turnstile) that can't be replicated from a plain script — did not attempt to work around this. Fallback worth implementing instead: on a real API auth failure, transparently re-run the existing `performPasswordLogin` (already implemented) if `SPOND_USERNAME`/`SPOND_PASSWORD` or the new `--username`/`--password-file` login flags were used, rather than requiring the user to notice and manually re-run `spond-mcli login`.
- HTTP interface for the MCP server (`spond-mcli mcp` is currently stdio-only). Add an HTTP transport so it can run remotely instead of only as a locally-spawned child process. Token passthrough via request header (e.g. `Authorization: Bearer <token>`) instead of `SPOND_TOKEN`/token file, since a remote server can't read the caller's local `~/.config/spond/token`. Intended user sequence: (1) `spond-mcli login` locally to obtain/save the token, (2) configure the MCP connection in the agent — the agent needs clear instructions on where that token goes (which config field, which header) when pointing it at the remote HTTP endpoint. **Done**: implemented (`src/http-server.ts`, `src/http-auth.ts`), Dockerfile added, deployed and verified end-to-end against a real deployment over HTTPS with token passthrough working. No server-side persistence needed (auth is stateless per-request via header).

## Completed

- Two more remote-MCP context-saving ideas (3.2.0, additive): (1) `get_events`/`get_posts`/`search_all`/`search_files` now surface a truncation note when more results exist than `maxResults` — implemented as a `note` field on `ToolCallResult`, rendered as a *second* text content block in the MCP response rather than changing the JSON data shape, so existing parsers of `content[0]` see no change. Detected via a generic `withTruncationCheck` helper (fetch `limit + 1`, check if the extra item came back, slice down to `limit`) applied uniformly across all four tools without touching their underlying `SpondCore` methods or the CLI. (2) Added the MCP **Prompts** capability (previously unused — only `resources`/`tools` were declared): a new `src/prompts.ts` with one canned prompt, `upcoming_events_for_group`, that hands the agent a correct worked `query` example instead of it discovering the syntax through a failed-attempt retry (each retry burns a full round-trip of context). Verified end-to-end against the real API over both stdio and HTTP.

- MCP tool consolidation + discoverability fixes (3.0.0, breaking): an overlap/simplification audit ("any overlaps between commands? simplifications and joins that could be made?") plus the deferred discoverability audit were done together and both fully addressed. 21 MCP tools → 17: merged `convert_pdf_to_text`/`convert_docx_to_text`/`convert_xlsx_to_text` into one `convert_resource_to_text(resourceId)` that auto-detects the format from the file's content type (persisted at download time in a new `meta` workspace namespace alongside the existing `raw`/`text` ones, read back via `getConverterCommand()` in `domain-logic.ts` — previously unused for this routing); merged `get_attachment`/`get_group_file` into one `get_file(url, groupId)` (they were already aliases underneath); retired `get_events_by_group`/`get_posts_by_group` by absorbing an optional `groupName` into `get_events`/`get_posts` (the `get_posts` path is a strict capability improvement over the old narrower tool — `groupName` now composes with `type`/`createdAfter`/`createdBefore`/`query`, which `get_posts_by_group` couldn't do). Added a genuinely new `get_my_members` tool (previously CLI-only). Renamed `get_events`/`get_posts`'s `max` param to `maxResults` for consistency with every other tool (the real Spond API's `max` query param is unaffected, translated at the `processToolCall` boundary). Fixed the remaining discoverability gaps found: `get_posts`'s 5-result default, `get_upcoming_events`'s `addProfileInfo` default asymmetry with `get_events`, and `get_events`'s `scheduled=true` default silently excluding cancelled events (same class of bug as the original `addProfileInfo` incident) are now called out in their descriptions; `search_events`/`search_posts` now note `search_all`+`query` as the more capable alternative. The CLI is entirely unaffected — none of the underlying `SpondCore` methods it calls directly were removed, only the MCP tool schemas/`processToolCall` cases layered on top of them.

- MCP tool `annotations` (2.3.0): all 21 tool definitions now carry standard MCP `readOnlyHint`/`destructiveHint`/`idempotentHint` annotations (`ToolAnnotations` in `src/spond-core.ts`) — 19 read-only tools marked `{ readOnlyHint: true }`, `accept_event`/`decline_event` marked `{ readOnlyHint: false, destructiveHint: false, idempotentHint: true }` (repeated calls converge on the same end state, and nothing is destroyed/irreversible — you can decline after accepting). Gives MCP clients a structured signal to distinguish safe-to-call-freely tools from the two that mutate state, instead of only being inferable from description prose. Purely additive.

- Fixed three real CLI bugs found by an adversarial audit of the local `spond-mcli` command surface (2.2.2), separate from the MCP tool interface (the CLI calls `SpondCore`/`cli-args.ts` directly, bypassing `processToolCall`, so the MCP-side validation fixes above didn't cover it): (1) `--help`/`-h` was indistinguishable from a typo — both hit the same `parseArgs` returns `null` → USAGE-dump-to-stderr + exit 1 path, since docopt was invoked with `help: false` and nothing special-cased it; added `isHelpFlag()` (`src/cli-args.ts`) checked before `parseArgs`, printing USAGE to stdout with exit 0 for a genuine help request. (2) Any plain `Error` (not `CoreError`) thrown during a real command — e.g. no token configured, or a real API failure like an expired token — crashed with a raw unhandled Node stack trace instead of a clean message, since `main()` had no top-level `.catch()`; most `SpondClient` methods throw plain `Error`, not `CoreError`, so this hit the two most common real-world failure modes, not just edge cases. Fixed by wrapping the top-level `main()` call. (3) `--max abc`/`--max 0`/`--max -5` all silently misbehaved (empty results with exit 0, or JS `slice(0, -5)` semantics silently dropping the last 5 results) instead of erroring — added a shared `parsePositiveInt()` helper in `cli-args.ts` used at all 9 `--max` parsing call sites, throwing a clear `Error` that now surfaces cleanly thanks to fix (2). Verified all three against the built CLI directly (exit codes, stdout/stderr separation, message content) rather than just unit tests, since these are process-level behaviors.

- Fixed a real, severe `search_all`/`search_events`/`search_posts` bug found by an adversarial audit (2.2.1): `maxResults` was silently capping the *raw fetch window*, not the result count — `SpondClient.searchEvents`/`searchPosts` and `SpondCore.searchAll`'s per-type post fetches all fetched only the `maxResults` most recent raw records, then filtered by `searchTerm` afterward, so a real match outside that narrow window was invisible. Made worse by the 2.2.0 default `maxResults` change (50→20). Confirmed and fixed against the real API: `search_events({searchTerm: "Vinterferieklubben", maxResults: 3})` went from 0 matches (wrong) to 2 (correct), independent of `maxResults`. Fix: decouple the raw-fetch window from `maxResults` (`SEARCH_SCAN_WINDOW`/`SEARCH_ALL_POST_SCAN_WINDOW` constants, fetch 200 then filter then slice to `maxResults`) in `src/spond-client.ts`/`src/spond-core.ts`. `SpondClientFake` didn't reproduce the `searchEvents`/`searchPosts` half of this bug (its dedicated search methods already filter-then-slice correctly) — the real bug was only visible against the real API, or via the `searchAll` post-scan-window path which the fake's shared `getPosts` truncation *does* reproduce; new regression tests cover both a direct real-`SpondClient` mock (`__tests__/unit/spond-client-search.test.ts`) and the fake-based `searchAll` path. Also fixed three smaller validation gaps the same audit found on `search_events`/`search_posts`/`search_all`: non-string `searchTerm` crashed with a raw JS TypeError instead of a clean `InvalidParams`; invalid `maxResults` (negative/non-numeric) leaked a raw upstream HTTP error instead of failing fast; `maxResults: 0` silently returned `[]` instead of being rejected per the schema's own stated `minimum: 1`.

- MCP token-usage audit + fixes (2.2.0): measured real response sizes for all 21 tools against a real account. Compact JSON responses instead of pretty-printed (`JSON.stringify(data, null, 2)` → no indent) in `mcp-server.ts` — an 8.9% size cut on every response for free. Fixed a real bug: `convert_xlsx_to_text` failed on every real spreadsheet because `ssconvert` couldn't infer the output format from an extensionless resource path — fixed by passing `--export-type=Gnumeric_stf:stf_csv` explicitly (`src/file-converter.ts` gained an `extraArgs` param) instead of relying on path extension, covered by a real end-to-end regression test. Lowered `get_events_by_group`/`search_all`'s default `maxResults` from 50→20 (their real-world default responses were the two largest, 25-29KB) — MCP-tool-layer only, CLI keeps its own 50 default. Added the JMESPath `query` param (see below) to `get_events_by_group` too, since it was missing there despite being the single largest-by-volume tool audited — same pattern as the other five. Trimmed JMESPath example counts in tool descriptions from 3 to 2 to reduce the fixed `tools/list` schema payload. Confirmed with real numbers: `search_all` with a filtering query dropped from 29,021 to 3,080 bytes (89.4% reduction) on real data.

- JMESPath `query` param (2.1.0, additive): `get_events`, `get_posts`, `search_all`, `search_files`, and `get_groups` accept an optional JMESPath `query` string so an agent can filter/project the result server-side instead of ingesting the whole collection into context — the same "grep, don't ingest" idea as `search_resource_text`, applied to structured JSON instead of file content. New `src/jmespath-query.ts` (`applyQuery`) wraps `jmespath.search`, rewrapping any parse/eval error as `CoreError(InvalidParams, ...)` with the bad query string in the message. `get_events`/`get_posts` destructure `query` out of `params` before the rest reaches the real Spond API call (`this.spondClient.getEvents`/`getPosts`) — confirmed via a `jest.spyOn` regression test that it never leaks into the actual API request. `get_groups`'s schema previously had `additionalProperties: false` (the only one of the five that did) — removed rather than allowlisted, matching every other tool schema in the file. Each tool's description carries 2-3 real worked examples derived from its actual response shape (`createEventSummary`/`createPostSummary`/`createGroupSummary`/`toFileSearchResult`/`searchAll`'s merged shape), not fabricated generically. Extracted `CoreErrorCode`/`CoreError`/`ToolCallResultType` into `src/errors.ts` (re-exported from `spond-core.ts` for compatibility) to avoid a circular import between `spond-core.ts` and the new `jmespath-query.ts`. Checked `jmespath` (npm) directly before adding it: v0.16.0, last published 2022, zero runtime dependencies — stale but the JMESPath spec itself is frozen, and no better-maintained alternative was found. Purely additive (no existing caller's behavior changes when `query` is omitted), so shipped as a minor bump rather than a breaking one like 2.0.0.

- HTTP mode file isolation + context-minimizing content access (2.0.0, breaking change): per-token workspace directories (`os.tmpdir()/spond-mcli-workspaces/<sha256(token)>`, `src/workspace-manager.ts`) isolate concurrent HTTP users' file operations from each other — same token always resolves to the same directory, so it survives across HTTP's stateless-per-request model without any in-memory registry. `get_attachment`/`get_group_file` no longer take a caller-supplied `filePath` (meaningless over HTTP, since that path lands on the remote container, not the client) — they download into the workspace and return an opaque `resourceId`. `convert_pdf_to_text`/`convert_docx_to_text`/`convert_xlsx_to_text` take that `resourceId` instead of `inputPath`/`outputPath`, returning a capped preview + lineCount rather than the full document. New `search_resource_text(resourceId, searchTerm)` tool greps the converted text server-side (case-insensitive substring match) so an agent finds what it needs without ingesting the whole document into context. Unified onto stdio too rather than keeping a dual schema, since this was already breaking. TTL-based sweep (24h default, hourly check, `.unref()`'d) evicts stale workspaces on the HTTP server; stdio uses a per-process `mkdtempSync` dir cleaned on exit. `resolveResourcePath` sanitizes/rejects path-traversal attempts so one HTTP caller can't escape their own workspace. Along the way, fixed a real bug caught during manual end-to-end verification: the `text/` namespace directory was never created before a converter binary wrote into it, so every conversion failed with an I/O error until `fs.mkdir` was added before the `convert()` call — now covered by a regression test using a real minimal PDF through the real `pdftotext` binary. Verified end-to-end against the real API over HTTPS: `get_group_file` → `convert_pdf_to_text` → `search_resource_text` chain against a real PDF group file, correctly isolated between two different bearer tokens. Full design in `/Users/anderssv/.claude/plans/sharded-dancing-popcorn.md`.

- Unified search (`spond-mcli search <term>`, MCP tool `search_all`): Searches across everything at once — events, plain posts, polls, and payment requests — in one call, tagging each result `kind: "event"|"post"`. Along the way: fixed a real bug where the post `type` filter used `PAYMENT_REQUEST`, but the real API's query param is `PAYMENT` (returning items whose actual `type` is `CLUB_PAYMENT`) — `--type PAYMENT_REQUEST` was silently 404ing. `SpondPost` now models `poll` (question, description, options with vote counts) and `clubPayment` (title, amount, status) since polls/payments are posts with that data embedded, not top-level title/body. `createPostSummary` falls back to `poll.question`/`clubPayment.title` when title/body are absent, and surfaces vote counts and payment status/amount. The narrower `search-events`/`search-posts` commands are kept for when you only want one type. Also fixed: the MCP server (`spond-mcli mcp`) only read `SPOND_TOKEN` and never fell back to `~/.config/spond/token` like the CLI does and the README already promised — now it does. Verified end-to-end against the real API (found and correctly enriched a real poll and two real club payments).

- Fix user/pw login (`spond-mcli login`): Replaced the Playwright browser-scraping login as the default with direct email/password authentication, matching the request/response shape documented in the community `spond` Python package (`POST /core/v1/auth2/login` with `{email, password}`, response `{accessToken: {token, expiration}}`). Credentials come from `SPOND_USERNAME`/`SPOND_PASSWORD` or an interactive terminal prompt (password input hidden via a small raw-mode reader in `src/prompt.ts`). Error messages only surface Spond's documented safe diagnostic fields (`error`, `errorKey`, `errorCode`, `message`) — never 2FA challenge tokens or phone numbers. Kept the old Playwright flow available as `spond-mcli login --browser` for accounts with 2FA enabled, since direct email/password login can't complete a 2FA challenge. Verified end-to-end against the real API — no more Chromium dependency for the default login path.

- My members command (`spond-mcli my-members`): Lists memberIds of everyone you're a guardian for, across all groups, with names and group names attached — no need to dig through event details to find the right memberId. Fetches `getGroups()` once, resolves matches via a pure `resolveMyMembers()` domain function, caches the result to `~/.config/spond/members.json` (0600 permissions) with a 5-minute TTL so repeated calls don't hit the API. On refresh, only rewrites the cache (and logs to stderr) if the resolved member list actually changed. Verified end-to-end against the real API.
